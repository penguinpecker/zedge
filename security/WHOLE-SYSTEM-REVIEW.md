# ZEDGE whole-system implementation review

Review date: **2026-10-04**. This is a source review and test record produced by the same agent team that implemented the changes. **It is not an independent security audit, a formal proof, or authorization to accept customer funds.** Findings describe this repository and the recorded deployments, not every behavior of its upstream providers.

## Decision and scope

The public Base → Horizen oracle route is deployed, its sources are published, and a genuine historical Chainlink report was verified and delivered over the native messenger. The frontend now reads that deployment. A public-round keeper, an exact-price matching ledger, an SDK encryption evaluation, and an undeployed public collateral vault are implemented and tested within the limits below. **The confidential funded prediction exchange is not production-ready.** Trusted request admission, private custody integration, state availability and unilateral recovery remain missing security boundaries; Vela production support and licensing are also unresolved.

This review covers the Solidity oracle/registry/bridge/vault components; Go engine and native/WASI conformance; the isolated Vela SDK wrapper; the public chain reader; and the keeper's report authentication, signing boundary, fee/nonce accounting and restart behavior. It does not inspect secrets, purchase subscriptions, deploy the new vault, activate a keeper, or send new transactions. Current deployment facts are in [MAINNET.md](../contracts/deployment/MAINNET.md); the earlier baseline review is not evidence that all current contracts remain undeployed.

| Component | Established behavior | Boundary still excluded |
| --- | --- | --- |

Original schema-1 validation remains separate. | Wallet connection or a verified oracle route does not activate deposits, trading or privacy. No claim facility is connected. |

| Engine protocol v2 | Integer financial ledger, funded reservations, partial matching, IOC/cancellation, fees, settlement/redemption/withdrawal stages; exact positive int192 prices and explicit public-round binding. | Caller-supplied authenticated context is a required input, not an implemented authenticator. Ledger entries are not actual token custody. |
| Vela SDK evaluation | Real pinned SDK encryption/decryption with command/receipt domain checks, key locking and cancellation-race tests. | Measured production guest, authenticated ingress/time, attestation, state persistence or private financial settlement. |

No owner/sweep/TEE authority. | **Undeployed**; all holdings and flows are public. It does not convert engine balances into funded claims or recover encrypted balances. |

## Findings fixed during this review

The keeper findings below were identified by source review and corrected in `services/keeper`. The first five fixes were re-read and their regression suite was run separately from the implementer's run. Tests use controlled dependencies; they do not demonstrate continuous production operation.

| ID | Failure before correction | Correction and evidence |
| --- | --- | --- |
| K-01 | Latest report could be compared with a Base head captured before the API response, incorrectly treating a valid new report as a fatal future timestamp. | Fetch a fresh Base head after each report. A temporarily ahead report disables readiness without disabling cached settlement/void. Regression checks the per-feed fetch/head order. |
| K-02 | A backlog of old timeout voids could indefinitely outrank creation of future rounds. | Prioritize evidence actions, then future creation, then void backlog; retain deterministic deadline ordering. Priority regression added. This does not establish unlimited throughput. |
| K-03 | A canonically reverted transaction remained nonterminal, wedging restart. | Reconcile canonical reverted receipts into a terminal `reverted` state, retaining consumed nonce and fee reservation; never automatically repeat that action. Restart regression verifies no resend/wait loop. |
| K-04 | A crash after round creation but before saving discovery metadata could lose a round outside the rolling lookback. | Persist and fsync active-round metadata before any create signing/send. Restart reads retained rounds beyond lookback; never-created expired entries can be removed. Source ordering and retained-round regression checked. |
| K-05 | Malformed saved fee reservations, including negative values, could undermine the lifetime fee allowance. | Validate the full journal schema, identity, transaction/receipt fields, positive reservation and fee/gas consistency before use. Reject corrupted entries instead of repairing them implicitly. Adversarial journal tests added. |
| K-06 | Entitlement could expire between latest-feed preflight and historical report fetch; a 401/403 then stopped cached resolution and void handling. | Shared report-unavailability classification includes 401/403 in both paths. Source re-review and the 19-test rerun passed, including revoked entitlement reaching timeout recovery while blocking new creation. |
| K-07 | Signing or journal fsync could stall after deadline/nonce validation, allowing an already expired or stale intent to reach submission. | After the signed hash is durable, immediately recheck fresh Base and Horizen clocks/deadlines, latest/pending nonce and empty EOA code before constructing the sole sender. Code absence accepts exactly `undefined` or `0x`, rejecting malformed falsy RPC values. Failure retains the signed record as uncertain and blocks retry. Separate source review and final 20-test rerun passed; the new regression covers ten expiry/clock/signer mutations plus no retry. |

Additional keeper checks now reside at the signing boundary: exact approved target/chain/selector, zero value, reviewed immutable dependencies, latest/pending nonce agreement, both-chain deadline checks, bounded gas and max fee, persistent fee reservation, and receipt/transaction/block identity. A transaction hash and exact public intent are fsynced before the single send attempt, followed by the final fresh-clock/deadline/signer check; secrets and raw signed transactions are not saved. Uncertain/dropped hashes stop for operator investigation. Canonical reorg detection stops rather than inventing replacement state. Inclusion can still occur after a check or during a race: contract deadlines remain authoritative and the receipt may revert.

Other completed hardening includes exact engine price strings without float or uint64 narrowing; Solidity-compatible round/rules hashing while preserving distinct internal IDs; rejection of version-1 snapshots instead of implicit migration; terminal fully redeemed archive preconditions; schema-2 frontend dependency pinning; and the SDK lock-during-signature/account-generation races. These protections have local tests, not end-to-end production privacy evidence.

## Open release gates

| ID | Gate and practical impact | Evidence needed to close |
| --- | --- | --- |
| B-01 — critical financial boundary | **Funded private admission and custody are not connected.** A wallet signature proves intent, not admission before cutoff. A host-provided clock, request ID or `System=true` context must not become authority to credit deposits, trade or withdraw. | A reviewed measured guest/runtime and custody protocol binding chain, endpoint, app/code identity, canonical requests/deposits, prior root, next sequence, exact round/oracle identity, cutoff admission and withdrawal nullifiers; replay and asset-conservation tests against actual token effects. |
| B-02 — critical recovery boundary | **Latest private state and usable unilateral exit are absent.** A root or enclave key backup does not give users current authenticated balance witnesses. A public vault does not solve private-ledger recovery. | Durable encrypted state/history and authenticated freshness, independent data/witness availability, tested host/enclave failure recovery, and an exit protocol preventing concurrent private spend plus public claim. Explicit rollback/reorg rules and recovery drills. |
| B-03 — external production gate | **Supported production Vela deployment and rights are unestablished.** The inspected v0.2.0 sources/docs still describe coordinated test environments and future production/self-service work. Inspected BSL terms do not grant this production financial use. Self-hosting alone does not resolve either issue. | Authenticated production endpoint/measurement and operational support/recovery policy, plus applicable production license/permission. See the dated [source refresh](../research/vela-integration-refresh.md), with pinned code and official terms. This is a source/terms reading, not legal advice. |
| B-04 — privacy boundary | **Encryption does not hide all metadata or make fills anonymous.** The inspected Vela manager receives event recipient IDs; raw deposit-result INFO logging can export application state. Public funding/claims, gas payer, timing, reports and aggregate outputs remain observable. | Remove/restrict unsafe output paths in the deployed measured build; role-specific encrypted results, reviewed logging/telemetry, disclosure/governance rules and adversarial leakage tests. Separately authorize user support exports and audit/deanonymization access. Never advertise fully anonymous fills from this SDK evaluation. |
| B-05 — external service access | **Continuous signed report access has not been demonstrated.** Chainlink username/HMAC-secret subscription access is separate from explorer credentials. A public historical fixture is not an entitlement or fresh feed. | Real subscription entitlement supplied privately by the operator; positive/denied/rotated credential checks; sustained exact-boundary retrieval and delivery tests within immutable deadlines. No credentials were inspected in this review. |
| B-06 — operational readiness | **A public keeper exists but has not been activated or endurance-tested here.** Three observed confirmations are not L1 finality; relay latency is variable. Journal/round/history limits and finite lifetime gas allowance can stop service. | Supervision and durable backups; alerts for report/access/relay/code changes, fee exhaustion, stuck hashes and stale locks; explicit finality policy; capacity, outage, failover and restart drills. Approve gas separately from user collateral. Do not describe the observed 24-second smoke arrival as a guarantee. |
| B-07 — public custody launch | **The new public vault is undeployed and not connected to retail UI or a matcher.** It has no private custody semantics and no owner rescue. | Pin reviewed registry/runtime/rules/token governance at deployment, complete transaction UI/allowance disclosures and recovery flows, and assess external review before customer funds. A future bridge from private balances must atomically remove the private claim when issuing the public claim. |
| B-08 — bounded ledger/product completeness | **Engine operating limits are deliberate, not production capacity evidence.** Account/evidence/lifetime-deposit limits remain; treasury fee withdrawal is not implemented. Hash-chain archival requires retained receipts and does not itself supply archive data. | Defined operational capacity and migration/retention policy, durable authenticated archival, treasury policy/implementation, and actual service/API integration with idempotent effects. No hidden bypass or automatic limit increase. |

Public quotes remain indicative rather than reserved fills. Publishing an aggregate book can disclose liquidity/timing even when individual records are encrypted. Public observers, the host/operator and each authenticated user have different visibility; product copy must describe the actual deployed boundary, not the strongest possible future architecture.

## Residual risks and dependency review

- The collateral is the pinned six-decimal Stargate-bridged **USDC.e**, not Circle-native USDC on Horizen. Token governance, bridge, issuer freeze/blacklist/upgrade and RPC/operator dependencies remain. Exact transfer-delta and deficit checks reject tested fee/rebase behaviors; they cannot certify arbitrary future token logic.
- The public vault's direct donations are permanently unallocated. Its shared reentrancy guard intentionally prevents forwarding/redeeming newly received shares inside an ERC1155 callback; a later call works. Approved ERC1155 operators can transfer holdings and redeem holdings they own. These are documented interface consequences, not confidentiality features.
- The keeper's doubled rollup data/operator estimates are **estimates**, not enforceable caps on separate rollup charges. Its local journal protects restart accounting, not a fully compromised signer host. Unknown signed hashes are never automatically replaced or resent.
- The current whole-contract Slither run retained 17 Low timestamp observations and one Low guarded publisher benign-reentrancy observation. Timestamp checks implement the intended round policy but inherit chain/sequencer timing assumptions. The new vault's focused run reports no High/Medium/Low findings; mixed pinned dependency pragmas remain informational.
- Engine `x/crypto@v0.54.0` has four disclosed **unused module-only** SSH/OpenPGP advisories. Native Go 1.27.1 `govulncheck` found no reachable or imported-package vulnerabilities. The fixed v0.56 line requires Go 1.26 while the current TinyGo scenario build uses Go 1.25.14. This is a documented compatibility residual, not a clean whole-module bill of health. See [engine/README.md](../engine/README.md).
- The isolated `@horizen/vela-common-ts@0.2.0` evaluation transitively includes `elliptic@6.6.1`, covered by [GHSA-848j-6mx2-7j84](https://github.com/advisories/GHSA-848j-6mx2-7j84). The latest owner-run npm audit reports two Low entries for the dependency and affected parent, representing one underlying advisory with no offered fix. The SDK is excluded from the frontend bundle. Root/frontend dependency audit reports zero vulnerabilities; this does not erase the SDK finding or establish production suitability.
- Horizen's explorer reports both deployed contracts verified with a **partial-match classification**. Published sources/settings/constructors and exact creation/runtime bytes were separately checked. The compiler metadata contains no source hash (`bytecode_hash=none`), consistent with the upstream classifier's limitation; the exact deployed explorer backend version is unknown. Do not label these fully/perfectly verified.

### Public RPC availability follow-up

The production browser received HTTP 429 with a 900-second Retry-After from the
pinned Horizen public endpoint. Initial repeated verification made 113 RPC
method calls, including 20 runtime downloads, per pass. The final frontend shares
monotonic per-endpoint cooldowns across clients, disables automatic retries,
honors bounded numeric/HTTP-date Retry-After, and pauses polling in hidden tabs.
Successful **read-only** route checks are retained in RAM for at most 120 seconds,
keyed by network and the entire manifest, with their completion time displayed.
The TTL starts before verification; errors and checks exceeding the window are
not cached. Fresh round/head reads remain on a 30-second visible-tab interval.
Refresh invalidates success but shares pending work and never bypasses cooldown.
Expired verification removes the displayed round. No cache authorizes a signature,
deposit or trade; keeper verification is separate and uncached.

These changes reduce avoidable load; they do not establish a production RPC SLA.
The official Horizen [JSON-RPC reference](https://docs.horizen.io/horizen-chain/api-reference/json-rpc/)
listed only Caldera HTTP and WebSocket access at review time. No independently
verified public fallback was added. Production operation needs a provisioned RPC
capacity/availability policy and measured outage behavior. The earlier live
browser failure must not be relabeled as a passed route verification.
