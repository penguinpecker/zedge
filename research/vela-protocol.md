# Vela protocol feasibility for ZEDGE

Research access date: **2026-10-04**. Scope: the confidential execution infrastructure needed for a BTC/ETH 5-minute and 15-minute **binary prediction market**, with a private order book, confidential balances, and independently specified event settlement. This is an evidence review and implementation recommendation, not an independent security audit. No third-party code was executed, no wallet was connected, and no transaction was submitted.

## Decision

**Proceed with an original, protocol-independent prediction-market core and a strictly test-only Vela adapter. Do not put real funds or production personal/trading data into the presently documented Vela environments.** Vela is technically relevant to hiding resting orders and internal ledger state from public observers and the ordinary compute host. Production feasibility remains conditional on licensing, supported deployment access, a reviewed trust model, authenticated inputs and time, capacity, recovery, and independent audits.

The strongest near-term deliverable is a deterministic matching/accounting engine with adversarial tests, connected to the approved ZEDGE interface through an adapter boundary. Demonstrate confidentiality on a genuine attested testnet deployment once access and applicable test licensing are confirmed. A local software enclave demonstrates integration behavior; it does **not** demonstrate hardware confidentiality. The official roadmap still describes local/testnet access and places Base mainnet, shared multi-app service, and self-service deployment ahead. [Vela roadmap](https://docs.horizen.io/vela/roadmap/)

There are two particularly concrete launch gates:

- The inspected Vela core, Go common library, TypeScript client, and Nova example use **Business Source License 1.1**. Its baseline grants copying, modification, redistribution and non-production use. Their Additional Use Grants specifically describe internal evaluation/testing and grant no production use; this should not be read as eliminating the baseline non-production rights. Publicly available source is not sufficient production permission. Obtain a written applicable production license/grant before embedding these components in a production build, and confirm the classification of a public hosted pilot with the licensor. The stated eventual change license is Apache 2.0 after the specified four-year period, not Apache today. [Core license](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/LICENSE), [TypeScript license](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/LICENSE), [Go license](https://github.com/HorizenOfficial/vela-common-go/blob/fb4e716f197a4d761350f5d93a97708b5d972bee/LICENSE), [Nova license](https://github.com/HorizenOfficial/vela-nova/blob/44f609353a554ef66ddb739706b22df687edbef5/LICENSE)
- Horizen Labs' terms expressly restrict test environments to experimentation and prohibit real financial assets and production data there. A definitive agreement may govern a production service. This is a separate access/terms issue from a GitHub license. [Horizen Labs terms, Vela section](https://horizenlabs.io/terms)

## Privacy and trust model

Vela is a **TEE confidential coprocessor**, not a zero-knowledge order-book protocol. A genuine Nitro Enclave isolates execution from its parent host; the application receives plaintext inside that boundary. P-521 ECDH and AES-256-GCM protect client/enclave messages. Encryption at rest protects stored state. Attestation identifies the approved enclave runtime and keys; signed state transitions are verified by contracts. This does not prove matching logic, solvency, oracle truth, or fairness mathematically. [Vela introduction](https://docs.horizen.io/vela/introduction/), [SDK cryptography](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/crypto/p521.ts)

| Observer/boundary | What ZEDGE can reasonably aim to hide | What remains visible or trusted |
| --- | --- | --- |
| Public ledger observer | Order price, size, side, user ledger balances and matches kept only in encrypted state/events | Sender/facilitator, app ID, request IDs/types and timestamps, ciphertext size, token deposits, withdrawal recipient/amount, gas, public application events and state roots. [Request/event definitions](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/Structs.sol), [endpoint interface](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/interfaces/IProcessorEndpoint.sol) |
| Ordinary host/operator | Plaintext encrypted to the approved enclave and held only there | Availability, network metadata, storage availability, scheduling and configuration remain dependencies; enclave output policy can leak data intentionally or accidentally. |
| Enclave/application | Nothing from the matching logic itself: it needs plaintext to execute | Correctness of WASM, runtime, parsing, cryptography, enclave image and oracle authentication. |
| Authorized auditor | Disclosure can be limited to designed report fields | Report authorization is managed on chain, and application code decides retained/reportable data. Report capabilities are not automatic legal compliance. [Smart-contract reference](https://docs.horizen.io/vela/reference/smart-contracts/) |
| Frontend, wallet and analytics | Enclave encryption can protect data after submission | Browser code handles plaintext and keys; compromised assets, logging, session replay, extensions or signing workflows can bypass privacy before encryption. This is an application threat-model implication. |

Do not promise anonymity, untraceable deposits/withdrawals, protection against every MEV strategy, or complete operator independence. An encrypted order still has timing, inclusion, censorship and output leakage. A public exact depth ladder is deliberate disclosure of aggregate strategy; a dark-book design should expose explicitly chosen delayed/coarsened metrics instead. Public price discovery and private resting interest need separate product contracts.

The official general privacy page uses stronger “ran correctly” wording than the dedicated Vela introduction. Use the narrower engineering description: authenticated execution of specified code under the TEE trust model, **not** a proof the code implements correct financial rules. [Privacy tools](https://docs.horizen.io/horizen-chain/privacy-tools/)

### Privileged controls and upgrade implications

- `TeeAuthenticator` is `Ownable`. Its owner can change the accepted PCR0 measurement and activate an enclave signer/key after attestation verification. There is no built-in timelock or multisig in this class; a deployed owner could itself be a governance contract, which was not verified. Changing approved code is a material confidentiality event. Publish measurements and require monitored, delayed governance plus an exit/migration policy. [Pinned authenticator](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/TeeAuthenticator.sol)
- `AuthorityRegistry` owner can replace per-application/default authority checkers. `DefaultAuthority` owner can add/remove permitted report requesters. The ability to choose report access is a privileged disclosure path, even if ordinary server operators cannot read enclave memory. ZEDGE needs a public report schema, retention policy and constrained authorization governance. [Authority registry](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/AuthorityRegistry.sol), [default checker](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/DefaultAuthority.sol)
- Endpoint administration includes fees, queue/capacity and deployment permissions; the status updater is privileged. Token allowlisting has independent administration. The dev-only reset role must be disabled at construction. Do not deploy the local reset configuration with valuable collateral. [Endpoint source](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/ProcessorEndpoint.sol), [allowlist](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/TokenAllowlist.sol)
- The inspected core uses constructor-initialized non-proxy contracts. A UUPS document describes a proposed change, not an implemented migration guarantee. Migration and trapped-funds handling must be designed against the actual deployed version. [Upgrade design](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/docs/design/UPGRADABLE_CONTRACTS_DESIGN.md)
- Nitro attestation verification imports a Horizen fork of Marlin's NitroProver. Request its exact version, deployment and audit coverage too; validating only the ZEDGE guest module leaves the attestation trust chain unchecked. [Verifier provenance](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/nitro_prover/README.md)

## Keys, restoration and rollback

### Enclave keys

The runtime keyset separates AES state encryption, secp256k1 result signing and P-521 communication keys. The current Executor configuration distinguishes unsafe development recovery (type 0, plaintext master-key recovery material) from AWS KMS recovery (type 1, Nitro-attested envelope decryption). The starter configuration selects type 0. Never promote that configuration to a confidentiality deployment. [Keyset types](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/executor/types.go), [Executor configuration](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/executor/config.go), [local environment file](https://github.com/HorizenOfficial/vela-starterkit/blob/85529cb769cd07a0f89cb959ba62c334a9cf5a9f/dockerfiles/.env.dev)

AWS KMS policies can condition decryption on enclave measurements. This requires a reviewed policy that denies unintended decrypt paths and restricts who can amend it. Backups alone do not make keys recoverable: restoration needs the encrypted state/version history, encrypted keyset/recovery material, a functioning KMS key, appropriate IAM/policy, and a permitted enclave image. Test loss of the parent host, KMS outages, accidental policy change and complete replacement deployment. AWS hardware and KMS are part of the trust/availability stack. [Vela KMS implementation](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/executor/kms/kms_client.go), [AWS attestation/KMS policy documentation](https://docs.aws.amazon.com/enclaves/latest/user/kms.html)

Require a documented key-rotation protocol: handling queued ciphertext for the old communication key, maintaining decryptability of historical events, state re-encryption, signer activation/revocation, interrupted migration, and rollback. The presence of `updateTee` does not demonstrate all of these lifecycle guarantees. Enclave debug mode must be excluded; AWS documents all-zero PCRs for debug enclaves. [AWS cryptographic attestation](https://docs.aws.amazon.com/enclaves/latest/user/set-up-attestation.html)

### User keys

The SDK derives a P-521 key from a wallet signature over a default challenge formed by `horizen` plus wallet address, then HKDF. Defaults do not contain an application, origin or chain context. Consequently the derivation signature is sensitive secret material: another party obtaining the same signature can derive the same key. Do not treat it like a shareable login proof, store it in telemetry, or use it in a server authentication flow. Browser/app isolation and a reviewed, context-bound key design are production prerequisites. Challenge overrides exist at a lower-level helper but are not an automatic interoperable migration solution. [Wallet derivation](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/crypto/wallet.ts), [constants](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/constants.ts)

Test deterministic signing across supported wallets, hardware wallets and account abstraction. A changed signing implementation or lost account can affect access to historical encrypted events. Define recovery, re-association and revocation explicitly. Static ECDH does not, by itself, establish forward secrecy for public historical ciphertext if a long-lived key is later compromised. Never export a wallet's secp256k1 private key merely to use a convenience helper for event subtype seeds. These are design requirements derived from the SDK's key and encryption flow, not claims of a demonstrated exploit. [P-521 implementation](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/crypto/p521.ts), [seed helpers](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/crypto/seed.ts)

Re-association overwrites the current per-address public key in application data; subsequent response encryption uses that key. It does not rewrite old on-chain ciphertext. Historical decryption therefore needs the original user private key and the enclave public key used at encryption time. The SDK's `decryptAndFilterEvents` fetches the **current** enclave public key/current derived user key and silently skips decryption errors. A rotation can consequently resemble missing history. ZEDGE needs explicit key epochs, historical public-key discovery, protected retention/recovery of necessary user keys, and an “unable to decrypt” state distinct from “no activity.” Re-registering the same key is not recovery from losing a different old key. [Key map](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/common/appdata/types.go#L123), [association/encryption](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/executor/executor.go#L645), [SDK history decryption](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/blockchain/client.ts#L284)

### State integrity is narrower than recovery and anti-equivocation

Observed protections are useful but bounded:

1. The Executor decrypts state and verifies its SHA-256 against the supplied state root. It also compares the supplied WASM fingerprint to the fingerprint retained in encrypted application data. This binds a transition to state/code content; it does not independently establish that the supplied root is the latest finalized chain state. [Executor checks](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/executor/executor.go#L555)
2. The endpoint accepts the head of **either** the normal queue or the trigger queue, and also requires matching application ID/current previous root and an authenticated transition signature. `getNextPendingRequest` gives triggers priority for the Manager's normal selection, but `stateUpdate` does not enforce a single global FIFO or require that priority across the two queue heads. The signature covers both roots, request ID, event arrays, withdrawals and fee/error fields. These checks reject stale canonical transitions after a different transition has been accepted. [Endpoint stateUpdate](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/ProcessorEndpoint.sol#L517), [queue selection and acceptance](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/ProcessorEndpoint.sol#L872), [signature verifier](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/AbstractTeeAuthenticator.sol)
3. The Manager compares local and chain roots, can roll back to a retained known version after its reorg timeout, and fails when it cannot find the chain's state version. This supplies operational reconciliation, not independent availability or a cryptographic proof of an honest RPC. [Manager reconciliation](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/manager/manager.go#L510)

ZEDGE must distinguish **signed**, **chain included**, **safe/finalized**, and **settled** states. An encrypted database backup does not prevent a host presenting an old state to a cloned enclave, private pre-finality conflicting receipts, withholding the latest state, or replay across improperly isolated deployments. The inspected state signature and request-ID hash do not explicitly domain-separate by chain ID and endpoint address. Require unique deployment keys and upstream analysis of domain binding, enclave clones, fork/reorg behavior, and request authenticity; do not assume complete anti-equivocation. This is an unresolved assurance question, not a proven vulnerability. [Request ID definition](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/ProcessorEndpoint.sol#L930), [signature payload](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/AbstractTeeAuthenticator.sol)

The Executor's `validateRequest` includes a TODO for reconstructing the request ID to verify request parameters received from the Manager. Request authentication across this host/enclave boundary merits focused upstream review before relying on sender, deposited amount, type or timing as trusted matching-engine inputs. No exploit was executed or established in this research. [Pinned validation code](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/executor/executor.go#L522)

## Integration shape, latency and economics

The supported documented guest path is Go compiled with **TinyGo 0.39.0** to WASI. Implement `deploy`, `load_module`, `deposit`, and `process_request`; `trusted_request` is optional for trigger flows. `DEANONYMIZATION` now uses `process_request` with report invariants. Keep the exchange core separate from this ABI, and use integer collateral/share units with deterministic market rules. [WASM development](https://docs.horizen.io/vela/reference/wasm-development/)

The documentation's 50-entry history warning is a **Nova sample application policy**, not an established Vela platform storage ceiling: `MaxTransactions = 50` is declared in Nova's guest `types.go` and `recordTransaction` truncates its array in `app.go`. Do not copy that retention policy into ZEDGE. Durable encrypted financial history needs its own retention, availability, recovery and reporting design. [Nova types](https://github.com/HorizenOfficial/vela-nova/blob/44f609353a554ef66ddb739706b22df687edbef5/runtime/wasm-go/app/types.go#L13), [Nova truncation](https://github.com/HorizenOfficial/vela-nova/blob/44f609353a554ef66ddb739706b22df687edbef5/runtime/wasm-go/app/app.go#L23)

A minimal adapter would associate an encryption key, encrypt typed requests locally, submit through the endpoint or authorized facilitator, track the request through completion, decrypt private user events, and reconcile against finalized state and custody. The official browser package provides encryption, submission, event lookup and claim helpers. **A submission receipt/request ID is not a completed order or fill.** [Pinned client](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/blockchain/client.ts)

Two source/documentation inconsistencies need explicit integration tests:

- The documentation labels the second `VelaClient` constructor argument as `useSoftwareTEE`; the inspected SDK implements **`useAlternativeSign`**, which selects a wallet signing method. It is not an attestation switch. Production authenticity must be checked against the actual authenticator/deployment. [Client documentation](https://docs.horizen.io/vela/reference/typescript-client/), [client implementation](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/blockchain/client.ts#L46)
- The actual SDK and endpoint protocol constant is **0**, distinct from product release version 0.2.0 and contrary to some README sample calls using 1. Read/version-check the deployed interface rather than copy snippets. [SDK constants](https://github.com/HorizenOfficial/vela-common-ts/blob/c9d28e4107d08ed4a570449a577ac07089891344/src/constants.ts), [endpoint constants](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/ProcessorEndpoint.sol#L32)

The current batching design document explicitly describes one request per blockchain block and approximately **30 requests/minute on a two-second chain**, with sequential fetch → execute → state transaction → receipt. This is an engineering estimate in a design document, **not a measured SLA**. The Manager defaults to a five-second polling interval, so a deployed configuration can be slower. Proposed batching improvements must not be counted as shipped capacity. Place/cancel/replace/balance/report activity all compete for processing. A visually fast ticker has no bearing on private matching throughput. [Batch design](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/docs/design/BATCH_EXECUTION.md), [poll configuration](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/manager/config.go)

No public dollar-denominated production fee schedule, p95/p99 latency commitment, throughput guarantee, recovery-time objective or availability SLA was located. Actual costs include on-chain request/update/claim gas, application fuel, sponsorship, enclave hosting, KMS, storage and indexing. Application fuel values are developer-assigned; the runtime applies its configured unit price and minimum. Obtain a deployed fee model and benchmark realistic order/cancel mixes before quoting user fees or accepting a five-minute-market latency budget. [Executor fee configuration](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/pkg/executor/config.go)

An enclave cannot fetch an oracle directly. Trigger contracts can pass plaintext application events and enqueue a higher-priority trusted follow-up; callbacks are isolated with `try/catch`, and chaining needs termination. This is not an automatic authenticated BTC/ETH settlement service. Oracle provenance, publication time, exact cutoff, tie rule, stale-feed behavior, finality and cancellation boundaries require a separately reviewed protocol. [Trigger reference](https://docs.horizen.io/vela/reference/trigger-contracts/)

The inspected `process_request` call passes application ID, sender, request type, payload and state; it does **not** pass the chain request timestamp or request ID as a trusted guest parameter. A user's supplied timestamp or a browser clock cannot enforce a market close. A proposed on-chain trigger/oracle callback can supply time and round evidence only after its authentication and failure semantics are established, and it adds processing work. No current ABI guarantee of authenticated guest time was established. ## Production acceptance gates for ZEDGE

These are proposed acceptance criteria, not claims about existing Vela guarantees.

| Gate | Evidence required before opening it |
| --- | --- |
| License and access | Written production rights for all imported components; supported environment/account/service agreement; named support/security contacts. |
| Authentic deployment | Verified contracts and dependencies, reproducible enclave image and guest WASM, approved measurement, chain/app domain, current governance and reset disabled. |
| Request/time trust | Documented and tested binding of sender, asset, type, payload, sequence, chain and endpoint; authenticated time/market cutoff and oracle evidence available to the guest. |
| Financial correctness | Original binary-share matching, full collateralization, reservation accounting, partial fills, cancellation race semantics, fees, withdrawals, deterministic resolution, conservation and replay tests. No leverage/liquidation/perp semantics. |
| Privacy | Explicit leakage budget for depth, trades, events, ciphertext metadata, oracle actions, deposits/withdrawals and audits; no plaintext observability; measured enclave deployment test. |
| Recovery and exits | Restore latest finalized state and keys; reorg and duplicate handling; safe communication-key rotation; a user exit path when operator/enclave unavailable. Existing `claim` of already credited funds is insufficient by itself. |
| Capacity | Realistic p50/p95/p99 submission, cancellation and finality measurements under bursts, outage recovery, large state and adversarial requests; bounded queues and documented overload behavior. |
| Security assurance | Version-specific reviews covering custody contracts, guest accounting, SDK cryptography/key handling, attestation/NitroProver, KMS/IAM, updater roles, oracle and web supply chain; resolved findings and an applicable incident/bounty policy. |
| Controlled launch | Audited, monitored, capped pilot on a supported production environment only after preceding gates; evidence of reserve/custody reconciliation and tested emergency procedures. |

The no-forced-exit issue is material: the inspected contract exposes claims only after a withdrawal/refund has become a pending claim, and its custody comments acknowledge no recovery mechanism for residual funds of decommissioned apps. A production private balance cannot rely solely on the continued availability of the same operator/keyset. Determine the actual supported exit/recovery design with the protocol team before selecting custody architecture. [Claims/custody interface](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/interfaces/IProcessorEndpoint.sol), [custody implementation](https://github.com/HorizenOfficial/vela/blob/335724c95ba7b58d64ec97bbb67d18640123278e/contracts/contracts/ProcessorEndpoint.sol)

The Builder Fund is compatible with a staged plan: it favors meaningful privacy implementation, has an early technical milestone, an audit milestone with an approved auditor, and a mainnet-usage milestone. A private prediction market is not one of the two named core RFPs; frame it as complementary/wildcard unless the Foundation agrees otherwise. Funding is competitive and terms are negotiated; a UI demo alone does not establish a production product or demand. [Season 2 program](https://horizen.io/builder-fund/)

Recommended initial implementation scope: one collateral asset, four BTC/ETH duration families, one matching application, encrypted orders and account history, authenticated settlement inputs, a deliberately limited public aggregate feed, explicit submission/processing/finality states, and an original conformance test suite. Keep Vela-specific code and configuration isolated until the licensing and deployment gates are satisfied. No production claim should be inferred from this research or from a successful local demonstration.
