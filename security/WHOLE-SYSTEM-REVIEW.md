# ZEDGE whole-system implementation review

Review date: **2026-10-04**. This is an internal source review and test record produced by the same team that implemented the changes. **It is not an independent security audit, a formal proof, or authorization to accept customer funds.** Findings describe this repository and the recorded deployments, not every behavior of its upstream providers.

**Update 2026-10-05.** An internal audit after this review found defects in the registry's void rule, the keeper's failure handling and the engine's deadline clock. The registry reviewed here is retired and its replacement is not deployed, the keeper is rewritten, and the engine protocol is version 3. Statements below marked *[Superseded 2026-10-05: …]* describe the 2026-10-04 state. The current position is in [Audit and fix program](#audit-and-fix-program-2026-10-05) at the end of this record. Unmarked statements were not changed by that work.

**Update 2026-10-06.** By owner decision the replacement registry's planned void grace is 300 seconds instead of seven days, which makes forced refunds (audit finding D4) an accepted risk; see [Audit and fix program](#audit-and-fix-program-2026-10-05).

## Decision and scope

The public Base → Horizen oracle route is deployed, its sources are published, and a genuine historical Chainlink report was verified and delivered over the native messenger. The frontend now reads that deployment. *[Superseded 2026-10-05: the registry in that deployment is retired, and there is no round state to read until its replacement is deployed.]* A public-round keeper, an exact-price matching ledger, an SDK encryption evaluation, and an undeployed public collateral vault are implemented and tested within the limits below. **The confidential funded prediction exchange is not production-ready.** Trusted request admission, private custody integration, state availability and unilateral recovery remain missing security boundaries; Vela production support and licensing are also unresolved.

This review covers the Solidity oracle/registry/bridge/vault components; Go engine and native/WASI conformance; the isolated Vela SDK wrapper; the public chain reader; and the keeper's report authentication, signing boundary, fee/nonce accounting and restart behavior. It does not inspect secrets, purchase subscriptions, deploy the new vault, activate a keeper, or send new transactions. Current deployment facts are in [MAINNET.md](../contracts/deployment/MAINNET.md); the earlier baseline review is not evidence that all current contracts remain undeployed.

## Findings fixed during this review

The keeper findings below were identified by source review and corrected in `services/keeper`. The first five fixes were re-read and their regression suite was run separately from the implementer's run. Tests use controlled dependencies; they do not demonstrate continuous production operation. *[Superseded 2026-10-05: the keeper was rewritten after the audit. K-03, K-05 and K-07 describe behaviour that the audit found unsafe for a sole operator and that has been replaced. For all seven rows the [keeper README](../services/keeper/README.md) describes the current behaviour.]*

| ID | Failure before correction | Correction and evidence |
| --- | --- | --- |
| K-01 | Latest report could be compared with a Base head captured before the API response, incorrectly treating a valid new report as a fatal future timestamp. | Fetch a fresh Base head after each report. A temporarily ahead report disables readiness without disabling cached settlement/void. Regression checks the per-feed fetch/head order. |
| K-02 | A backlog of old timeout voids could indefinitely outrank creation of future rounds. | Prioritize evidence actions, then future creation, then void backlog; retain deterministic deadline ordering. Priority regression added. This does not establish unlimited throughput. |
| K-03 | A canonically reverted transaction remained nonterminal, wedging restart. | Reconcile canonical reverted receipts into a terminal `reverted` state, retaining consumed nonce and fee reservation; never automatically repeat that action. Restart regression verifies no resend/wait loop. *[Superseded 2026-10-05: a reverted action is attempted again under a new attempt number, with spacing and a daily limit; never repeating it left the boundary unpublished and the round to void.]* |
| K-04 | A crash after round creation but before saving discovery metadata could lose a round outside the rolling lookback. | Persist and fsync active-round metadata before any create signing/send. Restart reads retained rounds beyond lookback; never-created expired entries can be removed. Source ordering and retained-round regression checked. |
| K-05 | Malformed saved fee reservations, including negative values, could undermine the lifetime fee allowance. *[Superseded 2026-10-05: the allowance is now a rolling 24-hour budget per chain; journal validation remains.]* | Validate the full journal schema, identity, transaction/receipt fields, positive reservation and fee/gas consistency before use. Reject corrupted entries instead of repairing them implicitly. Adversarial journal tests added. |
| K-06 | Entitlement could expire between latest-feed preflight and historical report fetch; a 401/403 then stopped cached resolution and void handling. | Shared report-unavailability classification includes 401/403 in both paths. Source re-review and the 19-test rerun passed, including revoked entitlement reaching timeout recovery while blocking new creation. |
| K-07 | Signing or journal fsync could stall after deadline/nonce validation, allowing an already expired or stale intent to reach submission. | After the signed hash is durable, immediately recheck fresh Base and Horizen clocks/deadlines, latest/pending nonce and empty EOA code before constructing the sole sender. Code absence accepts exactly `undefined` or `0x`, rejecting malformed falsy RPC values. Failure retains the signed record as uncertain and blocks retry. Separate source review and final 20-test rerun passed; the new regression covers ten expiry/clock/signer mutations plus no retry. *[Superseded 2026-10-05: this check gated Horizen-only calls on the Base clock and endpoint, and a signed-but-unsent record wedged every restart. It is removed. The same nonce is now signed again with a higher bid, which cannot repeat an effect because a nonce executes once.]* |

Additional keeper checks now reside at the signing boundary: exact approved target/chain/selector, zero value, reviewed immutable dependencies, latest/pending nonce agreement, both-chain deadline checks, bounded gas and max fee, persistent fee reservation, and receipt/transaction/block identity. A transaction hash and exact public intent are fsynced before the single send attempt, followed by the final fresh-clock/deadline/signer check; secrets and raw signed transactions are not saved. Uncertain/dropped hashes stop for operator investigation. Canonical reorg detection stops rather than inventing replacement state. Inclusion can still occur after a check or during a race: contract deadlines remain authoritative and the receipt may revert. *[Superseded 2026-10-05: upstream dependencies are no longer pinned by the keeper, there is no both-chain deadline check, gas and fee bounds are derived from live fees within a per-transaction share of the daily budget, and uncertain hashes and a reorganisation of the last settled transaction are handled without stopping. See the update.]*

Other completed hardening includes exact engine price strings without float or uint64 narrowing; Solidity-compatible round/rules hashing while preserving distinct internal IDs; rejection of version-1 snapshots instead of implicit migration; terminal fully redeemed archive preconditions; schema-2 frontend dependency pinning; and the SDK lock-during-signature/account-generation races. These protections have local tests, not end-to-end production privacy evidence.

## Residual risks and dependency review

- The collateral is the pinned six-decimal Stargate-bridged **USDC.e**, not Circle-native USDC on Horizen. Token governance, bridge, issuer freeze/blacklist/upgrade and RPC/operator dependencies remain. Exact transfer-delta and deficit checks reject tested fee/rebase behaviors; they cannot certify arbitrary future token logic.
- The public vault's direct donations are permanently unallocated. Its shared reentrancy guard intentionally prevents forwarding/redeeming newly received shares inside an ERC1155 callback; a later call works. Approved ERC1155 operators can transfer holdings and redeem holdings they own. These are documented interface consequences, not confidentiality features.
- The keeper's doubled rollup data/operator estimates are **estimates**, not enforceable caps on separate rollup charges. Its local journal protects restart accounting, not a fully compromised signer host. Unknown signed hashes are never automatically replaced or resent. *[Superseded 2026-10-05: an unmined hash is replaced by signing the same nonce again with a higher bid.]*
- The current whole-contract Slither run retained 17 Low timestamp observations and one Low guarded publisher benign-reentrancy observation. Timestamp checks implement the intended round policy but inherit chain/sequencer timing assumptions. The new vault's focused run reports no High/Medium/Low findings; mixed pinned dependency pragmas remain informational.
- Engine `x/crypto@v0.54.0` has four disclosed **unused module-only** SSH/OpenPGP advisories. Native Go 1.27.1 `govulncheck` found no reachable or imported-package vulnerabilities. The fixed v0.56 line requires Go 1.26 while the current TinyGo scenario build uses Go 1.25.14. This is a documented compatibility residual, not a clean whole-module bill of health. See [engine/README.md](../engine/README.md).
- The isolated `@horizen/vela-common-ts@0.2.0` evaluation transitively includes `elliptic@6.6.1`, covered by [GHSA-848j-6mx2-7j84](https://github.com/advisories/GHSA-848j-6mx2-7j84). The latest owner-run npm audit reports two Low entries for the dependency and affected parent, representing one underlying advisory with no offered fix. The SDK is excluded from the frontend bundle. Root/frontend dependency audit reports zero vulnerabilities; this does not erase the SDK finding or establish production suitability.
- Horizen's explorer reports both deployed contracts verified with a **partial-match classification**. Published sources/settings/constructors and exact creation/runtime bytes were separately checked. The compiler metadata contains no source hash (`bytecode_hash=none`), consistent with the upstream classifier's limitation; the exact deployed explorer backend version is unknown. Do not label these fully/perfectly verified.

### Public RPC availability follow-up

The production browser received HTTP 429 with a 900-second Retry-After from the
pinned Horizen public endpoint. Initial repeated verification made 113 RPC
method calls, including 20 runtime downloads, per pass. The final frontend shares
monotonic per-endpoint cooldowns across clients, disables automatic retries,
honors bounded numeric/HTTP-date Retry-After, and pauses polling in hidden tabs.
Successful **read-only** route checks are retained in RAM for at most 120 seconds,
keyed by network and the entire manifest, with their completion time displayed.
The TTL starts before verification; errors and checks exceeding the window are
not cached. Fresh round/head reads remain on a 30-second visible-tab interval.
Refresh invalidates success but shares pending work and never bypasses cooldown.
Expired verification removes the displayed round. No cache authorizes a signature,
deposit or trade; keeper verification is separate and uncached.

These changes reduce avoidable load; they do not establish a production RPC SLA.
The official Horizen [JSON-RPC reference](https://docs.horizen.io/horizen-chain/api-reference/json-rpc/)
listed only Caldera HTTP and WebSocket access at review time. No independently
verified public fallback was added. Production operation needs a provisioned RPC
capacity/availability policy and measured outage behavior. The earlier live
browser failure must not be relabeled as a passed route verification.

## Audit and fix program (2026-10-05)

An internal audit on 2026-10-05 re-examined the deployed route, the keeper, the engine and the chain interface. It was done by the same team with proofs of concept on local chains and forks; it is not an independent audit. Findings and their dispositions are tabulated in the [verification record](README.md#audit-and-fix-program-2026-10-05). This section restates the parts of this review that changed. Nothing here has been deployed.

**Decision.** Unchanged: the confidential funded exchange is not production-ready and gates B-01 to B-08 stay open. In addition, the public round layer cannot operate until the replacement registry is deployed and checked.

| Component | Position after the fixes |
| --- | --- |
| Streams contracts | Three live and unchanged: the Base adapter and publisher and the Horizen price cache. The registry deployed on 2026-10-04 is retired with zero rounds. Its replacement is in source behind a UUPS proxy and is not deployed. Rules: an opening must be recorded within 210 seconds or the round can be voided; resolution is accepted at any time at or after the end, from the cached closing price; an opened round can be voided only strictly after end + 60 s + 300 s (the void grace, seven days until the owner decision of 2026-10-06) and only while no closing price is cached; tie-Up and the payout ratios are unchanged. The owner can upgrade the registry or transfer ownership in two steps, and cannot renounce. An upgrade can change any rule or stored result. |
| Public round keeper | Rewritten. Every action it sends is permissionless and either idempotent or self-rejecting, so a failure is waited out and retried instead of ending the process. It stops only when continuing could double-spend, overspend, or act for a chain, contract, registry implementation, owner or signer it cannot identify. An action somebody else already took counts as done. Resolution is attempted whenever the closing price is cached, however late, and the keeper voids no round that the registry does not itself report as Voidable. Spending is limited by an operator-set budget per chain over a rolling 24 hours, with at most one twentieth of it for a single transaction. It refuses to run against a release that is only planned. |
| Engine protocol | Version 3. Open, resolve and void commands carry the registry block time that included the event; windows are judged at that time and never at the processing clock. Resolution has no deadline. A complete pair merges at any time. Version-1 and version-2 state and commands reject. |
| Public outcome vault | Still undeployed. It accepts only the replacement registry's version marker and pays what that registry reports, so it inherits the registry owner key as a trust assumption. |

**Accepted risk D4 (owner decision 2026-10-06).** The owner chose, knowingly, that an opened round whose closing price has not been cached six minutes after its end can be voided (1/2 + 1/2, not a refund of the price paid): void grace 300 seconds, so `voidableAfter = end + 360`. Normal rounds are unaffected; they resolve as soon as the closing price is cached (30 to 40 seconds after the end in the rehearsal), and a cached closing price still blocks any void. The rule also catches ordinary failures: an outage of the report service, the keeper's endpoints or the bridge lasting about eight minutes now voids the round too (the keeper voids about eight to nine minutes after the end), and the void is final even though the report could still be published later. Anyone can block Base-to-Horizen price delivery by pumping Horizen's deposit fee on Base, at a cost that grows with how long the block is held: at 2026-10-05 Base fees about 0.03–0.05 ETH for a few minutes and about 0.4 ETH per hour. One block stops every price message, so it voids every opened round that closes at that boundary at once (up to four at a quarter-hour: BTC and ETH, five and fifteen minutes). With a five-minute grace, a trader on the losing side with more than roughly that amount at stake across those rounds can profit by forcing the void, and the winners then receive half of what they were owed. **Open item: stake limits on the total exposure of all rounds closing at the same boundary, or a test-only launch, before real money.** Not built.

**Operating the keeper.** One `--watch` process per wallet under a supervisor, with its state directory on a local disk of one machine and the host clock synchronised (the report service rejects requests more than five seconds off). A registry upgrade or ownership change stops the keeper by design until a release file naming the new state is installed. A transaction sent by hand from the keeper wallet stops it and needs a new state directory. The public Horizen endpoint is rate limited; use a private one. The keeper has no market filter and no wind-down mode. The [keeper README](../services/keeper/README.md) lists every reason code, the stop conditions and the recovery for each.

**B-06 restated.** The keeper has still not been activated or endurance-tested. What changed is what can stop it: not a fee rise, a rate limit, a front-run step or a spent lifetime allowance, but an identity, signer or journal problem. A dress rehearsal on local forks (below) ran it through real rounds and five injected faults, in four runs of 24 to 30 minutes; that is not endurance and involved no real report service, bridge or fees. Still needed: real report credentials, a private Horizen endpoint, alerting on the status lines, and a first supervised round on mainnet.
