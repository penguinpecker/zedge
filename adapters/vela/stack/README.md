# ZEDGE Vela guest on the local Vela stack: evaluation slice

**EVALUATION ONLY.** This runs the ZEDGE guest (`../guest`) on Horizen's local Vela v0.2.0 Docker stack, on a throwaway Anvil chain (31337). The executor is a software TEE with fixed development keys and no attestation; the collateral is a worthless test token; the round registry runs on an unsigned fixture oracle; the sender, the amount and the time the guest sees are trusted from the manager. Nothing here is private, secure or production-ready, and none of it may be pointed at a public chain or real funds.

The protocol is [`../guest/README.md`](../guest/README.md). This folder runs all of it on the real stack: the time-free path (key, deposit, withdrawal, claim), the clock (§8), the two-phase order book (§9) and the registry round mirror (§10), for one market, BTC 15-minute rounds.

## Run

```sh
./run.sh                          # from clean volumes: build checks, bring-up, the slice, teardown, PASS/FAIL
KEEP_STACK=1 ./run.sh             # leave the stack up afterwards, for its logs (see below)
VELA_STARTERKIT=/path/to/clone ./run.sh   # take the starter kit from a local clone instead of GitHub
```

`KEEP_STACK=1` keeps the stack as the destructive phases leave it, which is no longer usable: the millisecond test has moved Anvil's time past anything the guest accepts, so every later tick fails with `malformed trusted payload` (Anvil time cannot go back), and the manager was killed mid-inclusion and then lost its database, so it processes nothing. Use it to read logs; start again with `./run.sh` for a working stack.

`run.sh` rebuilds the guest wasm (`../guest/build.sh`) when it is missing or older than any guest or engine source, the same rule the guest's wasm tests use, so a stale wasm is never deployed.

Needs Docker with the Vela v0.2.0 images pulled (about 3 GB) and room for the stack's volumes, Foundry 1.7, Node 22, `npm ci` done in `../../../contracts` (OpenZeppelin, for the trigger's tests) with `contracts/out` built (the registry artifacts), and the built guest (`../guest/build.sh`, TinyGo 0.39.0). It uses the starter kit's host ports 8545 (chain), 8000 (subgraph) and 8081 (authority service). A full run takes about 20 minutes, most of it the manager's 5-second polling (the starter kit's setting). Results go to `evidence/vela-slice-2026-10-06/` at the repository root (git-ignored).

## The trigger (`contracts/src/EvaluationClockTrigger.sol`)

An original contract (no upstream code) that holds nothing, moves nothing and answers the endpoint only. Its constructor fixes the endpoint, the registry (its proxy) and the one market (asset 0 = BTC, 900 s), which must equal the guest's `markets` parameter.

- A tick request of exactly 32 bytes (the time-free build) gets the 192-byte version-1 answer, unchanged.
- Anything longer gets the version-2 answer of guest README §10: it calls the registry's permissionless `createRound` for the market's next two slots, reads `getRound` for every asked ID and for the next slots it was not asked about, and returns the clock words plus at most 16 records, only where the registry is ahead of the engine. A request of any other shape, or one asking about more than 16 rounds, gets `n = 0`: a plain clock tick.
- Every registry call is a low-level call with a fixed gas limit: 250,000 for `createRound`, 60,000 for `getRound` and `roundIdFor`, each more than three times the honest cost measured against the real registry behind its proxy (69,000 and 16,000). Not Solidity's `try`/`catch`: that reverts the caller when an answer does not decode, so a registry upgraded into something that answers garbage would stop the clock. A read is accepted only if the answer is exactly 704 bytes (22 words), and only those bytes are copied, so a huge answer costs nothing here.
- Foundry tests (`forge test`, 20 tests): the version-1 answer and its fuzz; the version-2 answer against the real registry (creation of the next two slots, the selection rules word for word against `getRound`, opening, resolution, a void with the opening missing, the 16-record cap, malformed requests); registries that revert, loop until out of gas, answer 703, 705 or 40,000 bytes, have no code, or answer 704 bytes of `0xff` (16 well-formed records the guest then skips as undecodable); two fuzz tests that the answer never reverts and always carries the clock words, each under 1.8 M gas. The busiest honest answer (8 rounds asked, slots created) used 313,000 gas; the gas-burning registry 1.63 M.

Why the gas limits matter beyond the trigger: the endpoint calls the trigger inside a `try` that forwards all but 1/64 of its gas, and the manager sends its transaction with the gas the node estimates. A transaction in which the trigger runs out of gas still succeeds if the 1/64 left is enough to finish the request, so the estimate could settle on such a gas limit, and the tick would be lost without a trace, if the trigger's own cost were many times what finishing the request costs. Bounding every registry call keeps the trigger's worst case near 1.6 to 1.8 M gas (measured above), and a successful answer also costs the endpoint the storage of the payload. The stack run below checks the outcome directly: with the registry's code swapped for a gas burner, and then for a reverting stub, the tick still landed and applied. That is two hostile codes on one stack and the reasoning above, not a proof for every registry or every gas estimator.

## What the slice does and checks

1. **Bring-up.** Chain id 31337; endpoint code present; the TEE signer and enclave key on chain equal what the executor logs; image digests, contract addresses, role holders and the wasm SHA-256 go to `manifest.json`. Addresses are found on the chain itself: the kit writes them to an environment file in a volume, which is not read.
2. **Deployment.** A fresh throwaway operator deploys the test token, the `StreamsRoundRegistry` implementation behind an `ERC1967Proxy` with `MockStreamsBoundaryOracle` (from the read-only artifacts in `contracts/out`), then the trigger bound to that registry and market. The endpoint admin allow-lists the token through Anvil impersonation (no key is typed or read). The wasm goes to the authority service, then `submitDeployRequestWithTrigger` with `markets: [{"asset":"BTC","duration":900}]`. Checked: the registry's rules hash equals the engine's computation; the deploy completes; the application root is non-zero; the trigger is bound; the descriptor's wasm hash equals the built artifact and the upload's; the constructor parameters reach the chain byte for byte.
3. **Lifecycle.** Fresh random wallets funded with `anvil_setBalance`; keys stay in the process. Key registration without a seed (133 bytes), the bootstrap sync (its tick creates the next two rounds in the registry and in the engine), a deposit (receipt decrypted: credited amount, auto-registration), a withdrawal request (receipt decrypted, one `Withdrawal`), the claim, a second account withdrawing to a third address, and two private refusals: a withdrawal to the endpoint, and one to the trigger, with the trigger left holding no tokens.
4. **Negative cases.** Deposit before the first tick; deposit with no registered key; a second allow-listed token; ETH (refunded exactly); an exact duplicate command (a `retry` receipt, no second withdrawal); a 16,385-byte payload; a sync that `session.ts` encrypted without `../crypto/pad.ts` (guest README §4), refused for its length alone. Each is checked for its public error and its refund.
5. **Restarts, before any time is moved.** `compose restart executor manager` once the manager is idle, then `compose down` and `up` with volumes kept: the keyset is restored with the same signer, the chain keeps its state, and the next-nonce withdrawal after each restart is applied (the engine accepts only the previous nonce + 1, so the ledger was not rolled back).
6. **One round, then a void (BTC, 15-minute rounds).** Anvil's time control jumps between a round's moments, so the full 15-minute schedule needs no waiting and no shorter rounds. The keeper's calls (fixture observations written with `setCached`, `recordOpening`, `resolveRound`, `voidRound`) are made by the operator wallet, each mined at an exact second.
   - Round A was created by the trigger, in the registry and in the engine (the guest's next tick request lists it as scheduled). Its opening is written to the fixture oracle and recorded at start + 3; the next tick applies the registry's record (opening price, `registryTime` = the registry's `openedAt`).
   - Alice and Bob deposit; each deposit-only request is checked against the engine ledger (below), including both accounts' positions.
   - Alice mints 10 complete sets, for the engine round ID the client derives itself (SHA-256 of `{config, round}`).
   - Alice stages a resting sell of 10 Up at 60. Its tick activates it; her next request collects the outcome (applied, resting).
   - **The executor and the manager restart while her order rests.**
   - Bob stages a crossing IOC buy of 4 Up at up to 65. It fills 4 of Alice's 10 at her price, 60: the client computes the notional (2,400,000 atoms), the fee (24,000 atoms, 1 % to each side), what Bob pays (2,424,000) and what Alice receives (2,376,000), and checks Bob's fill (taker, buy, price, size, fee, no counterparty named) and Alice's view (filled 4, notional, fee paid, cash).
   - Alice stages a cancel of the remaining 6; it is applied and her 6 Up are free again.
   - **The cutoff, to the second.** With automine off, both staging requests are mined in one block; the slice then mines every block at the second it names: the first staging transition at cutoff − 1, its tick, the second staging transition at exactly the cutoff, its tick. The first order is admitted and rests; the checkpoint of the tick at the cutoff releases it before activating the second, which is refused with `round closed`.
   - Round A resolves Up in the registry (closing fixture at its end) and round C, the next slot, opens on the same boundary observation. One tick mirrors both, sweeps round A in each account's own name (Alice 6,000,000 atoms, Bob 4,000,000, each nonce up by one, the refused order having used none) and archives it; the archive record shows the fixture prices and outcome Up.
   - In round C Alice mints 4 sets and sells 2 Up to Bob at 40 (fee 8,000 atoms each side). Round C's closing price never arrives: the registry voids it at `voidableAfter` + 1, 311 s after its end (the 10 s observation window plus the 300 s grace of the planned mainnet profile, owner decision 2026-10-06), and the keeper voids the round starting at C's end, which the trigger created and nobody opened (opening missing). One tick mirrors both voids from the registry's own record, sweeps round C half-and-half (Alice, 2 Up and 4 Down: 3,000,000 atoms; Bob, 2 Up: 1,000,000) and archives both. The accepted risk of that short grace (audit finding D4): anyone can force such a refund by blocking Base-to-Horizen price delivery, for about 0.03–0.05 ETH for a few minutes at 2026-10-05 Base fees, so a losing trader with more at stake can profit and the winners get half; per-round stake limits are not built (`../../../protocol/README.md`). The fixture oracle here does not exercise it. A round voided for a missing opening can hold no shares (nobody can mint before the opening), so its settlement pays nothing; the half-and-half payout is shown on round C, which opened and was voided for a missing close.
   - Both withdraw (Bob everything, Alice all but 10 tokens, which the later phases use) and both claims move exactly that.
   - Every archive record of the run forms the engine's archive hash chain from its initial root, each digest recomputed by the client.
7. **Reconciliation, no tolerance.**
   - At every step of the rounds: token balance = app custody + pending claims; app custody = credited − withdrawn from the client's own totals; the `Withdrawal` events = the withdrawals the slice asked for; the trigger holds nothing.
   - Four times over the whole run (after the lifecycle, after the rounds, after the clock tests, at the end): those legs again from the endpoint's own books (custody = deposits − refunds − withdrawals + trigger returns; pending claims = refunds + withdrawals − claims paid), the second token and ETH, the state-root chain, every receipt 8,220 bytes with the one subtype, every completed request's ciphertext 2,076 bytes as the endpoint stored it (`requestById` at the submission block), every tick request answered by exactly one trusted request, every clock record equal to the asking block's number and time and to the Keccak-256 of the payload the trigger stored for it (checked against the trusted request's ID, which the endpoint derives from that hash, and against the payload read from the trigger queue at the asking block) and asking for no tick, failed, key and deposit-only requests asking for none.
   - The engine's own ledger at each of the four deposit-only requests made for it, from the state the executor logged for it (the leak below, used here as a reading): engine `custody` = app custody, `paidOut` = the `Withdrawal` events, `deposited` = the deposits credited, `claimable` = 0, and in the rounds `fees` = the client's own sum (64,000 atoms) and each trader's cash and holdings = the client's figures.
   - Positions: every receipt's view (`engine.AccountView`) against the client's own figures for cash, reservations, shares per round and orders, after every trading step.
   - Every version-2 trigger answer (42 in the run): read back from the endpoint's trigger queue at the asking block, its clock words are that block's, and its records are exactly those section 10 calls for, each equal to the registry's `getRound` at that block, word for word.
8. **Clock.** Every clock record equals the asking block's number and timestamp, including a block whose time Anvil was told to set and one an hour later. A tick lost because the trigger reverted (its code swapped, then restored byte for byte) is replaced by the next request's tick. With the registry's code swapped for a gas burner, then for a reverting stub, the tick still lands and applies, with no records. A block stamped in milliseconds makes the trusted request fail with `malformed trusted payload` and leaves the clock where it was.
9. **Destructive, last.** The manager is restarted in the second between its `stateUpdate` being mined and the manager seeing it included; then its data volume is removed. What happens is recorded (see the findings).
10. **Leak scan.** What the executor and manager logs hold in clear (`leak-scan.json`; counts, source lines and field names, no log text).
11. **Measurements.** Request latency, the executor's time per request and per tick from its own log timestamps, the state size the host logged for every request, requests and transitions per minute, ticks per request, activations per tick, the time from a staged order to its activation, trigger payload sizes and the gas of every asking and tick transition.

## Findings from the run of 2026-10-06

With the registry's void grace at 300 s (the planned mainnet profile; it was a day before) and the guest rebuilt for the engine's 120 s lower bound (wasm 548,604 bytes, SHA-256 `4d9bb2f3776f415ccd2719d01740df429ba6d9ef7abf70b188cdfbb37f611566`), `./run.sh` from clean volumes passed all 210 checks (manifest 5, slice 205) on colima (aarch64, 4 CPUs, 6 GiB) with the amd64 images under Rosetta, in about 16 minutes, the rounds phase 4.3 minutes, and tore the stack down. The numbers below are from its `slice.json`. (The run before it, with the one-day grace and after the review fixes: padded requests, the clock record's payload hash, the order cap at activation, the cancel probe, also passed all 210. A first run with the fixes stopped at a check of the slice's own: after the restarts it read trusted payloads again at blocks from before Anvil's restart, which Anvil no longer holds. The check now binds each clock record's hash through the trusted request's ID instead. Before the fixes, two runs passed the 205 checks of the time, within a few milliseconds and a few gas of each other.)

- **`MaxActivations` and `MaxSweeps` (decision 9) were not measured at their caps.** The busiest ticks here applied seven and eight engine commands (checkpoint, mirror, sweeps, archives) on states of about 6 KB in at most 10 ms; at the caps a tick can apply up to 53 commands, and the tests time one of 40 on a 389 KB state (guest README §9), which these accounts never approach. Reaching it through requests needs 32 accounts with 4 resting orders each, about 250 requests, roughly 40 minutes at the 5-second poll. Both stay 16, on the native measurements in the guest README (§9) only.
- **The trusted payload is readable from the chain.** The endpoint stores it in its trigger queue; `getNextPendingRequest` at the asking block returns it, which is how every answer above was checked against the registry. It is public, like the clock record.
- **The client must take its nonce from its latest view.** The settlement sweep redeems in the account's own name, so after a settlement each trader's next nonce was one higher than its own count; the slice reads it from every receipt.
- **A manager stopped while its transaction is in flight never recovers.** Restarted about 0.5 s after its `stateUpdate` was mined, the v0.2.0 manager rolls back its database; the chain has the new root, so on every start it logs "unrecoverable disalignment between DB and chain" and exits, and Docker restarts it in a loop. No request is processed again. Claims already credited are still paid (`claim` needs no manager); the application's custody has no way out. The slice therefore restarts only an idle manager.
- **With its data volume removed, the manager panics** ("State root mismatch … expected 0000…", then `panic: runtime error: slice bounds out of range [1:0]`) on every start and processes nothing. The executor regenerates the same signer, because the development keys are fixed.
- **Anvil does not keep an `evm_increaseTime` offset across `compose down`/`up`**, so the restarts run before any time is moved; afterwards the block time would go backwards and the guest would refuse every tick as `clock regression`, as specified.
- **The host wraps the guest's public errors**: on chain they read `failed to process deposit: zedge: …` or `failed to process request: zedge: …`. A deposit from an address with no key fails with the host's own `no Secp521r1_PubKey found` (error code 9) and is refunded.
- **Logs (`leak-scan.json`).** Every `deposit` result is logged at INFO (`pkg/wasm/wasmtime_runtime.go:582`): the whole guest state in clear (salt, engine ledger, staged commands and uncollected outcomes included) and the deposit receipt's plaintext with its recipient. The token, amount and sender of each deposit and the payload and state size of every request are logged too. No command or receipt plaintext was found anywhere else, decoded or not, and no user wallet key.

## What it shows and what it does not

Shown, on this machine, as an evaluation: the order build of the guest runs inside the emulated amd64 v0.2.0 executor with its trigger; rounds are created by the trigger in the registry and the engine in one tick; openings, a resolution and voids (an opened round one second past `voidableAfter` with the 300 s grace, and a round whose opening was missing) are mirrored from the registry's own records and times; a resting order, a partial fill at the maker's price, a cancel, the cutoff at the exact second, the settlement sweep and the archive behave as the guest README says; every amount the client computed on its own (fills, fees, proceeds, redemptions, half-and-half, withdrawals) matches both the receipts and the endpoint's custody; the engine's own ledger equals the chain at every deposit; an executor and manager restart with an order resting loses nothing; a registry that burns gas or reverts does not stop the clock.

Not shown, and not showable here: confidentiality of anything from the host (the executor logs the whole guest state on every deposit); that the guest's sender, amount, time or round records are genuine (the manager supplies them and v0.2.0 binds none of them; a manager could fabricate round records or hold ticks back, which the clock and archive records only make visible afterwards); attestation; oracle authenticity (the observations are unsigned fixtures); performance on real hardware, under load, or at the state bound; `MaxActivations` and `MaxSweeps` at their caps (above); behaviour with more than two traders, with more than one market, or across a 16-record payload on the endpoint (the Foundry tests cover the trigger's side of that, not the endpoint's storage of it); the public testnets. A green run is evidence about this local setup only.
