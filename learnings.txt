1. DIRECT ANSWER: PUBLIC ORDERS AND PRIVATE FILLS
------------------------------------------------
Yes: an application can publish selected order information while keeping fill
records, account balances, and positions in encrypted state and returning
encrypted personal receipts.

That does not mean the occurrence, price, size, or participants of every fill
will remain secret. Public order flow, exact book changes, receipt metadata,
funding transfers, and the application's own outputs can reveal information.
Executing inside a TEE does not undo information disclosed outside it.

Example: if all relevant orders and deterministic priority are public, a
100-share Up ask at 60 cents and a crossing 40-share buy may make the resulting
40-share fill at 60 cents reconstructible without decrypting its receipt.

A displayed remaining quantity falling from 100 to 60 reveals a 40-share
reduction. That alone does not distinguish a fill from cancellation/amendment;
public cancellation information or other observations may remove the ambiguity.

Public quotes or initial order announcements disclose less than a complete,
continuously updated, individually identified order book. Withholding updates
can also make announced liquidity stale. The interface must label what its
public feed represents and must not present stale announcements as guaranteed
executable liquidity.

2. WHAT THE SDK AND PLATFORM ACTUALLY SUPPLY
-------------------------------------------
Encrypted order instructions:
  The SDK has encryptForTee(). It obtains the configured enclave public key and
  encrypts the payload. submitRequest() submits supplied bytes; it does not
  automatically call encryptForTee(). [S1]

Encrypted personal execution receipts:
  User events support arbitrary recipient-encrypted application data. ZEDGE can
  define fill, order-status, balance, and position response schemas. There is no
  built-in prediction-market fill schema or exchange engine. [S1, S2, S3]

Confidential balances, positions, and P&L:
  The platform encrypts persisted application state. We can implement account
  and share ledgers inside it, subject to correct authorization/accounting and
  the output/logging issues described below. Encryption is not proof of
  solvency or financial correctness. [S2, S3]

Public quotes and selected liquidity:
  AppEvent is an intentionally public output channel. The application chooses
  which fields to publish. Full exact depth, aggregate depth, and delayed quotes
  have different information-disclosure consequences. [S1, S2, S4]

Limit orders, partial fills, cancellation, minting, merging and redemption:
  These are custom ZEDGE application logic. The generic SDK does not implement
  the matching rules, collateral model, market lifecycle, or settlement oracle.

Private conditional orders:
  A possible later application feature, not a supplied order type. Trigger
  thresholds can be private state, but authenticated price/time inputs, workload,
  output policy and deadline handling still need engineering and validation.

Hidden wallet identities and funding:
  Not supplied by the normal request/deposit/withdrawal flow. Gas sponsorship
  does not hide the recorded sender or facilitator. [S4, S5]

Hidden per-fill public token transfers:
  A normal public ERC-20 or outcome-token transfer exposes information even if
  a TEE decided to perform it. Internal collateral/share ledger updates can
  avoid a public token transfer for each fill; later funding and withdrawal
  activity remains observable.

Fast, fair five-minute markets:
  The SDK establishes neither a latency guarantee nor fair sequencing. Measure
  the full request/cancel/settlement path and validate timing before promising
  the experience. A fast chart or submission acknowledgement is not a fill.

3. ACTUAL INPUT, STATE, AND OUTPUT FLOW
--------------------------------------
Proposed ZEDGE flow using the reviewed primitives:

  Browser encrypts a signed/authorized order intent
    -> on-chain request and outside-enclave manager
    -> enclave decrypts and runs custom ZEDGE WASM
    -> internal collateral/share ledger and order state change
    -> encrypted participant receipts + deliberately selected public outputs
    -> signed state transition accepted on chain

Normal PROCESS payloads are decrypted before WASM execution. Sending plaintext
through ordinary submitRequest() is not a valid public-order toggle. The
contract-trigger TRUSTPROCESS path is a separate plaintext-input route. For a
public order feed, encrypt the ordinary request and explicitly publish approved
order or quote fields as application output. [S3]

The application result separates State, user Events, AppEvents, Withdrawals,
Report, Fuel and Error. User-event contents are encrypted for registered user
keys. AppEvents are not encrypted by that path. The SDK's getCurrentUserEvents()
decrypts user events, whereas getAppEvents() reads public application data.
Do not place private fill fields into AppEvents, withdrawals, error messages,
logs, analytics, URLs or other public output channels. [S1, S2, S3]

4. WHAT PUBLIC CHAIN OBSERVERS CAN STILL SEE
-------------------------------------------
The standard flow exposes request/application identifiers, sender/facilitator,
funding amounts and assets, timing, state roots, completion/error information,
runtime fees/refunds, and withdrawal recipient/token/amount. Encrypted events
still expose event count, ciphertext lengths, request association and subtypes.
UserEvent itself has no public recipient-address field. [S4, S5, S6]

An application subtype meaning FILL can disclose that a fill occurred even when
the contents are encrypted. Optional seeded subtypes obscure semantic labels,
but do not remove timing, counts, request linkage or other inference. [S3, S7]

The public application fee is the Vela runtime fee, not necessarily ZEDGE's
trading commission. Computation-dependent fees can become another information
channel. Public roots are commitments, not a public plaintext account ledger
or a proof that the custom financial rules are correct. [S3, S6]

Traders learn their own executions and can disclose them. Do not promise that
fills are secret from everybody or that encrypted execution is anonymous.

5. VERIFIED OPERATOR METADATA: RECEIPT RECIPIENTS
------------------------------------------------
The stock outside-enclave manager receives more information than the public
UserEvent shows:

  a. common.Event includes plaintext UserID, serialized as userId, alongside
     ciphertext. UpdatePayload includes these events. [S8]
  b. encryptEvents() encrypts event contents but retains the UserID field. [S3]
  c. The executor communication response returns the update payload to the
     manager. [S9]
  d. The blockchain client copies ciphertext and subtype into the on-chain
     event arrays and omits UserID there. [S10]

Consequently, emitting a maker receipt and a taker receipt for one match can
let the operator associate both recipient wallets with the same request.
This is source-evidenced recipient metadata disclosure; it is not evidence
that the manager decrypts the encrypted receipts.

Hiding trading relationships from the operator requires additional work on
the notification/output protocol. Deferred retrieval, batching, padding or
removing unnecessary recipient metadata are design candidates, not existing
SDK guarantees. Their remaining correlation and availability risks need review.

6. SOURCE-IDENTIFIED SENSITIVE LOGGING PATH
------------------------------------------
The reviewed WASM runtime logs the complete raw deposit result at INFO before
parsing it. DepositResult contains application State and user Events. These
are application outputs before the executor's later encryption step. [S2, S11]

The executor defaults to the network logger and INFO network level. The same
logger is supplied to the runtime; the provided network logger writes messages
over its connection, and the manager includes a receiving log server. [S12]

This is a concrete output path requiring removal/redaction and verification in
the target deployment. Do not claim account state is hidden from the operator
solely because persisted state and user receipts are encrypted.

Confidence boundary: this finding comes from static source tracing. We have
not observed a real Nitro deployment leaking state, demonstrated an exploit,
or established how any third-party hosted deployment is configured.

7. OTHER SDK DETAILS THAT AFFECT IMPLEMENTATION
----------------------------------------------
- The documented VelaClient boolean is labeled useSoftwareTEE, but the reviewed
  implementation calls it useAlternativeSign and uses it for wallet signing.
  It is not a hardware-attestation or privacy switch. [S1, S13]
- User encryption-key derivation uses a wallet signature over a default
  challenge formed from "horizen" and the wallet address. The signature must be
  treated as sensitive key-derivation material, not a shareable login proof.
  Default app/origin/chain separation and wallet compatibility need review. [S14]
- Re-association changes the current response key; it does not re-encrypt old
  events. Historical decryption needs the corresponding historical keys.
  decryptAndFilterEvents() uses current keys and skips decryption failures.
  The UI must distinguish undecryptable history from no history. [S1, S3]
- A request ID or successful submission is not an accepted order or a fill.
  Track submission, processing, confirmation, partial fills and settlement as
  distinct application states. [S1]
- The 50-record history cap mentioned in documentation belongs to the Nova
  sample. It is not an established Vela platform-wide storage ceiling. ZEDGE
  needs an explicit encrypted history/retention and recovery design; see the
  pinned sample evidence in research/vela-protocol.md.

8. RECOMMENDED ZEDGE DESIGN
---------------------------
Proposed product promise:
  Public market prices and selected liquidity information, with encrypted
  personal execution records and positions, subject to disclosed metadata.

Implementation requirements:
- Fully collateralized binary outcome shares. Lock one collateral unit to
  create one Up plus one Down share; the normal resolved payout is 1/0.
- Original deterministic matching and accounting, separate from Vela adapters.
- Integer balances, funded reservations, partial fills, safe cumulative fee
  rounding, cancellation races and replay/idempotency protection.
- Internal collateral/share transfers per fill; no automatic public token
  movement for every execution.
- Public quotes or deliberately chosen aggregated/delayed liquidity. Do not
  promise an exact public live book and completely uninferable executions.
- Private receipts and account views with explicit key-epoch handling.
- Remove sensitive logging and resolve host-visible recipient metadata if the
  promise includes confidentiality of relationships from the service operator.
- Verify the enclave measurement, application fingerprint, governance and real
  deployment configuration. A software emulator is not hardware confidentiality.

The first complete test slice remains one BTC 15-minute market. Add ETH and
5-minute rounds after measured settlement, cancellation, capacity and recovery
tests. These are proposed engineering steps, not implemented ZEDGE features.

9. PRODUCTION GATES FROM THE BROADER RESEARCH
--------------------------------------------
- Availability/licensing: the reviewed public release is documented for
  local/testnet use. The inspected BSL licenses grant non-production rights but
  no production-use grant. Obtain applicable permission and a supported,
  verified deployment; public source access alone is insufficient.
- Timing: the guest ABI lacks an authenticated chain-time parameter. A
  pre-cutoff checkpoint processed after the outcome is visible does not by
  itself solve late execution. Define and enforce commitment/cancellation rules.
- Request integrity: review binding of canonical sender, token/amount, request
  type, payload, domain and ordering across the host/enclave boundary.
- Sequencing: the manager prefers trigger requests, but the reviewed contract
  accepts either queue head. Normal manager scheduling is not a contract-level
  global priority guarantee.
- Oracle: a signed price proves authenticity, not necessarily selection of the
  first eligible boundary observation. Stork is documented on current Horizen;
  the Pyth deployment found was on legacy EON, not established on the new L3.
  The production oracle and exact observation rule remain unresolved.
- Recovery: claim() releases already approved pending claims. It does not
  independently release every private balance if execution stops permanently.
  State/key restoration and the selected emergency exit require design/tests.
- Capacity: upstream sequential-processing estimates are not a measured SLA.
  Benchmark actual placement, cancellation and settlement under adverse load.
- Security: independent version-specific reviews, remediated findings, output
  inspection, governance and operating permissions remain launch requirements.

frontend now exist. See security/README.md for the actual implementation boundary.

Public RPC operational finding — 2026-10-04

The deployed browser encountered Horizen HTTP429 (bandwidth limit) with an
advertised Retry-After of 900 seconds. Local full-route RPC verification had passed;
the failed browser visit did not establish a current verified route. Keep these
observations separate. The app correctly withheld unverified data.

poll intervals must not repeat that whole workload per visitor. Provider backoff,
bounded read-only verification freshness and hidden-tab pause are availability
requirements; they do not make the public endpoint a production availability SLA.

Audit and fix program — 2026-10-05
----------------------------------
An internal audit of the deployed route, the keeper, the engine and the chain
interface ran on 2026-10-05, with proofs of concept on local chains and forks.
It is same-team work, not an independent audit. No funds were at risk: no
contract holds money and the registry had zero rounds. The fixes are in source.
Nothing new is deployed and nothing was sent to a real chain.

State after the fixes: three contracts stay live and unchanged (the Base
adapter, the Base publisher and the Horizen price cache). The Horizen round
registry deployed on 2026-10-04 is retired. Its replacement is planned and not
deployed. Addresses and hashes are in contracts/deployment/MAINNET.md.

What the audit found, by class, and how each class was fixed

1. A timeout that pays out is an attack surface.
   The retired registry let anyone void an opened round one hour after its end
   and pay 1/2 + 1/2 when no result had been recorded. An outsider could cause
   that on purpose: each price message buys a fixed 924,355 gas of Horizen
   deposit capacity on Base, the deposit fee can be raised by anyone, and above
   roughly 18 to 20 gwei no publication fits into one Base transaction. The same
   void also fired when the closing price was already cached on Horizen and
   simply nobody had called resolve.
   Fix: a new registry. Resolution has no deadline. An opened round can be
   voided only strictly after end + 60 s + 7 days, and only while the price
   cache holds no closing price for it; otherwise the call reverts and the round
   must be resolved.
   Lesson: never let "nobody acted in time" move value between winners and
   losers. Make the timeout long compared with what blocking costs, and make it
   give way to evidence that exists.
   [2026-10-06: the planned grace is now 300 s, end + 60 s + 300 s, by owner
   decision. The first half of this lesson is knowingly not followed: blocking
   for a few minutes costs about 0.03-0.05 ETH. D4 is an accepted risk; see
   "Short refund window" at the end.]

2. Immutable everywhere leaves no repair.
   A billing, access or deactivation change at the upstream verifier would have
   stranded an immutable registry and every round on it.
   Fix: the registry is a UUPS proxy. The owner can upgrade it or transfer
   ownership in two steps, nothing else; renouncing is disabled. A test pins the
   storage layout, so an upgrade that moves a variable fails the suite.
   Cost: the owner key is a new trust assumption. An upgrade can change any
   rule and any stored result. The three route contracts stay immutable, so an
   upstream break still needs new route contracts; the registry can then be
   pointed at them.

3. A sole operator must not exit on routine trouble.
   The first keeper treated nearly every surprise as fatal: a fee above a fixed
   gas number, somebody else taking its next step, a rate-limited endpoint, a
   report that was not valid yet, any change in 16 pinned upstream dependencies,
   a lifetime allowance of about ten Base transactions, a signed transaction
   that never landed. It never retried a reverted publication. It sent one
   transaction per ten-second step, so six transactions plus the relay could
   miss the 210-second opening window at a 15-minute boundary. Every exit left
   rounds to be voided.
   Fix: a rewrite on four rules. (a) Exit only when continuing could
   double-spend, overspend, or act for a deployment or signer that cannot be
   identified. (b) "Somebody else already did it" is success. (c) "Not yet" is a
   wait with backoff that holds up only that action or that chain. (d) A
   reverted action is tried again under a new attempt number. Spending is
   limited by a rolling 24-hour budget per chain in wei; each transaction is
   priced from live fees and may take at most one twentieth of that budget.
   Each chain has its own lane, and neither waits for the other.
   Lesson: sort every failure into done, retry, skip or stop before writing the
   loop. Stopping is right for a signer that might double-spend. It is wrong
   for everything else when every action is permissionless and either
   idempotent or self-rejecting.

4. A mirror must judge events on the source's clock.
   The engine compared registry deadlines with the time at which it processed a
   command. A result mined at the deadline and processed a second later was
   rejected, and the engine would then pay 1/2 + 1/2 where the registry pays
   the winner. Its merge rule also differed from the vault's.
   Fix: protocol version 3. Open, resolve and void commands carry the registry
   block time of the event; windows are judged at that time, which only has to
   be no later than the engine's own time. A complete pair merges at any time.
   Lesson: mirror a chain event at its inclusion time. Mirror a void only from
   a recorded void, never from a clock or from a "Voidable" read. The old
   conformance run could not see this bug because it processed every event at
   its own timestamp; it now applies each event one second late.

5. Status text must cover dead ends.
   The chain interface said "Awaiting resolution" and "Awaiting opening
   observation" for rounds that were voided or could only be voided, and the
   rules text blamed "missing evidence" where the contract's trigger was that
   nobody had recorded the result in time.
   Lesson: write copy for every phase the contract can report, and name the
   trigger the contract actually uses.

6. A guard nobody asserts is not a guard yet.
   Several registry guards had no test, including the unknown-round check in
   voidRound; without it a round could be voided before it was created and
   would then be created already void. Each now has a test, and 55 scripted
   mutations of the registry were all caught.
   Test counts in the documents had drifted (106, then 131, now 152).
   Lesson: date every count and say which command produced it.

7. Check where evidence came from.
   The "one bridge message found by scanning" was the deployment account's own
   funding deposit. Both delivery timings on record, 23 s and 24 s, are
   self-generated. They show that the route works and nothing about load.

What remains a trust assumption

- The registry owner key. The planned owner is the deployment account.
- Chainlink. The first published report that covers a boundary wins, and that
  only one such report exists is Chainlink's guarantee, not something the
  contracts enforce. If no observation is produced within 60 seconds after a
  boundary, no report is acceptable for it.
- The OP Stack path. Sequencing and derivation decide when a message lands.
  Anyone can raise the deposit fee or resend stored observations without limit.
  This can still delay prices and cost the operator an opening.
- The opening window. An opening not recorded within 210 seconds voids the
  round before it trades. A five-minute round may trade for only 60 seconds.
- The seven-day lock. If a closing price can never be published, one-sided
  positions wait seven days for the void. Complete pairs can merge at any time.
  [2026-10-06: now six minutes after the end (300 s grace), and in exchange a
  few minutes of blocked delivery forces the half payout; see the end.]
- USDC.e, the verifier, the messengers and the portal keep their own owners.

What an operator must know

- Nothing runs until the replacement registry is deployed and the release file
  says so. The keeper refuses a planned release, except in rehearsal mode
  against local forks.
- An address is not an identity. 0xdD3bEAA92E5819333A5D5ccD185704427fAB0e91 is
  the retired registry on Horizen and the live adapter on Base. The planned
  implementation address on Horizen is the same string as the Base publisher.
  Always key on chain and address together.
- The planned registry addresses come from the deployment account's Horizen
  nonce. Any other transaction from that account on Horizen first changes both
  addresses and every round ID derived from them.
- At the registry address the code is a generic proxy. Verify the
  implementation slot, the implementation's code hash, owner(), pendingOwner()
  and the rules hash. The implementation's code embeds its own address, so its
  hash is only valid at that address.
- Pin the proxy address, never a version string. The bare implementation
  answers version() and accepts createRound and voidRound on its own empty
  storage. Never call proxiableUUID() through the proxy; it reverts.
- An upgrade or a new owner is a different deployment. The keeper stops on it
  by design, and the site must show mainnet as unavailable, until a reviewed
  release names the new state.
- "Voidable" on an opened round means only that seven days passed with nothing
  cached [2026-10-06: the grace is now 300 s]. The closing report stays verifiable on Base for about 30 days and a
  recorded void is final. Publish, relay and resolve first; void only when no
  report can be obtained. [2026-10-06: superseded. The keeper now voids two
  minutes after voidableAfter if the price is still not cached, also after an
  ordinary outage, although the report could be published later. See "Short
  refund window" below.]
- The keeper needs: one process per wallet under a supervisor; a state
  directory on a local disk, never a network share; a host clock within five
  seconds (the report service rejects anything further off); an endpoint on
  each chain that serves transaction receipts; a private Horizen endpoint (the
  public one has answered 429 with Retry-After 900). Do not run it from a
  timer in one-shot mode: relay timers and backoff live in the process.
- The keeper wallet is for the keeper only. A transaction sent from it by hand
  looks like a stolen key, stops the keeper, and needs a new state directory.
- Budget: one number per chain for a rolling 24 hours; a single transaction
  may reserve at most one twentieth of it. At 2026-10-04 fees a Base
  publication cost about 0.000007 ETH and there are 576 a day, so about
  0.004 ETH a day on Base and well under 0.001 ETH on Horizen. These are
  estimates, not measurements of sustained operation.
- Registry calls take empty evidence bytes. The price cache rejects anything
  else.
- An engine round must be created before its start, together with its registry
  round. A round the engine never created cannot be mirrored later.

Short refund window: owner decision 2026-10-06
----------------------------------------------
The owner chose, knowingly, that an opened round whose closing price is not
cached six minutes after its end can be voided (1/2 + 1/2, not a refund of
the price paid), instead of seven days later. The planned void grace is 300 s, so
voidableAfter = end + 60 + 300, six minutes after the end. The registry's
initialize now accepts 2 minutes to 21 days (was 1 to 21 days). Normal rounds
are unaffected: they resolve as soon as the closing price is cached (30 to 40 s
after the end in the rehearsal), and a cached closing price still blocks any
void. Nothing was deployed; the registry is still planned.

Accepted risk, audit finding D4. Anyone can block Base-to-Horizen price
delivery by pumping Horizen's deposit fee on Base. The cost grows with how long
the block is held: at 2026-10-05 Base fees about 0.03-0.05 ETH for a few
minutes and about 0.4 ETH per hour. One block stops every price
message, so it voids every opened round closing at that boundary at once (up
to four at a quarter-hour). With a five-minute grace, a trader on the losing
side with more than roughly that amount at stake across those rounds can
profit by forcing the void, and the winners then receive half of what they
were owed. An ordinary outage of about eight minutes (report service, keeper
endpoints, bridge) now also ends in a final void.
Open item: stake limits on the total exposure of all rounds closing at the
same boundary, or a test-only launch, before real money. Not built.

Keeper rule decided the same day for an opened round past voidableAfter with
no cached closing price: first relay it (if Base holds the observation) or
publish it (if Chainlink serves a covering report the Base adapter accepts).
Never void while a publication or relay the keeper sent is less than 90 s
old or not yet settled (at most ten minutes after its first signature).
Void when Chainlink's signed reports prove the window was skipped (the
first report at or after the boundary has validFromTimestamp <= boundary and
observationsTimestamp > boundary + 60, and the adapter rejects it with
InvalidOracleResponse in a simulation), or when the closing price is still not
cached two minutes after voidableAfter despite those attempts. This replaces
the ~30-day expiry rule above.

- One rule, many copies. The bound and the grace were pinned in the contract,
  the profile, two deployment scripts (plan-registry.mjs, broadcast-hybrid.mjs),
  the website's manifest parser, keeper tests and fixtures, and the engine's
  own bound and known answers. Changing the grace means regenerating the
  release (rules hash, configHash, implementation runtime hash, sample round
  ids) and every copy; the planned addresses stay because the deployer's
  Horizen nonce is still 2.
- The engine still encodes the one-day minimum (engine/oracle.go, VoidGrace >=
  86400) and its mainnet known-answer test still describes the seven-day
  config. It rejects the planned profile until it is updated, which is the next
  step. protocol/config.schema.json still says voidGrace minimum 86400; lower
  it to 120 in the same step. [Done later on 2026-10-06: VoidGrace >= 120 (to
  21 days, as initialize), known answers for the 300 s profile, schema
  minimum 120; conformance passes.]
- A guard counted from signing does not cover a transaction still on its way:
  Base can leave one out of its blocks for minutes. The keeper's in-flight
  guard counts from settlement, caps an unmined wait at ten minutes, and counts
  a hash its own replacement dropped (a newer boundary taking the nonce) as on
  its way until it was dropped (review fix, 2026-10-06).
- The broadcaster's fork rehearsals and the keeper dress rehearsal ran with
  the seven-day profile and build and have not been repeated.
